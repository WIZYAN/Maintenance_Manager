# 维保管理器

基于 Renesas RA4M1、24C256 EEPROM 和大彩 DC10600PM101 串口屏的双项目维保管理。工程入口位于 `Maintenance_Manager/src/hal_entry.c`，屏幕工程位于 `VisualTFT/Project/Project.tftprj`。

## 功能与计时规则

整机、传感器各有两项独立维保指标：

| 指标 | 默认周期 | 时间来源 | 断电期间 |
|---|---:|---|---|
| 日历保养 | 180 天 | 串口屏 RTC 正常经过的秒数，排除人工校时差值 | 继续计算（RTC 持续走时） |
| 开机使用 | 8000 h | MCU 的 1 ms SysTick | 不增加 |

开机时间内部按秒累计，界面向下取整显示小时，例如 `100h/8000h`。两个维保项目共用累计开机秒数，各自保存本轮的开机时间起点。
每个项目的进度条取以下两项中较大的比例，百分比向下取整，进度条最大显示 100%：

```text
已过天数 = 本轮累计日历秒数 / 86400（向下取整）
日历比例 = 本轮累计日历秒数 / (天数周期 × 86400)
使用比例 = 已用秒数 / (小时周期 × 3600)
进度条   = min(100%, max(日历比例, 使用比例))
```

例如已过 60/180 天、已使用 4000/8000 小时，进度条显示 50%。任一项达到周期即到期，进度条变红并显示“过期”；正常为蓝色、显示“健康”。
**数字不在周期处封顶**：可以显示 `181天/180天`、`8001h/8000h`。日历单位使用“天”，开机时间使用“h”，斜杠前后字号相同。
到期不会自动开启下一轮。修改周期保留起点；确认完成保养才同时重置该项目的日历天数和开机使用时间。

一天表示累计满 24 小时，与跨午夜无关。例如 23:59:59 开始，到次日 00:00:00 仍为 0 天，到次日 23:59:59 才为 1 天。进度条使用秒数计算，能够反映不足一天的进度。校时不会重置整机或传感器起点，也不改变开机小时累计规则。

所有业务计算、判断、校时补偿、颜色控制、复位和 EEPROM 保存均在 MCU 完成。屏幕无新增 Lua、变量绑定、控件联动或业务计时器。屏幕 RTC 控件 10 与 MCU 查询使用同一个系统时钟，但控件改为只读；用户通过新增校时输入框提交目标，由 MCU 修改 RTC 并保存补偿后的计时锚点。

## 代码分层

```text
Maintenance_Manager/
├── src/
│   └── hal_entry.c                   FSP 固定入口，调度模块 A 接口
└── Maintenance/
    ├── A_Maintenance.c / .h          外部业务接口，持有模块私有实例
    ├── F_Maintenance.c / .h          维保计算、协议、存储记录等模块功能
    ├── H_Maintenance.c / .h          RA UART、SysTick、GPIO、软件 I²C
    └── Maintenance_Config.h         配置宏
```

维保模块头文件按 `A_Maintenance.h → F_Maintenance.h → H_Maintenance.h` 向下包含，只定义接口所需类型、声明和宏，不含函数实现。其他模块只调用 `A_` 接口；A 层调用 F 层入口，F 层通过 H 层操作硬件。F 层内部的计算、协议、记录辅助函数集中在同一 `.c` 内并设为 `static`，避免导出仅供内部使用的函数。跨 `.c` 的 A/F/H 接口在头文件中注明调用范围。

`hal_entry.c` 不受模块分层和同名头文件规则约束，保留原来的 FSP 入口结构，包括 `R_BSP_WarmStart`、引脚初始化和安全构建代码；主循环只负责调用模块的 A 接口。维保模块自身的外设操作放在 H 层，`SysTick_Handler`、`DIS_Callback` 保留中断向量和 FSP 要求的名称。`ra/`、`ra_gen/`、`ra_cfg/` 中的厂商库及生成代码保持原状。

三个无参数入口继续保留。此次计时调整将 EEPROM 记录升级为 v4，并新增受控校时接口和屏幕输入控件；底层通信格式及循环日志提交顺序沿用原有实现。

## 调用接口

接入方无需创建上下文或单独调用初始化函数。主循环持续调用无参数任务接口，工程已接入：

```c
#include "Maintenance/A_Maintenance.h"

while (1)
{
    A_Maintenance_Task();
    // 其他非阻塞任务
}
```

两项复位接口同样无参数，返回值用于确认保存结果；周期设置接口只需传入周期数值。以下操作应在对应用户事件发生时调用，不要每个循环都执行：

```c
A_Maintenance_SetPeriodDays(150);          // 整机日历周期：保留原起点
A_Maintenance_SetSensorPeriodDays(180);    // 传感器日历周期
A_Maintenance_SetPeriodHours(8000);        // 整机小时周期：保留已用时间
A_Maintenance_SetSensorPeriodHours(8000);  // 传感器小时周期

A_Maintenance_Reset();        // 整机：从当前累计日历秒数、开机秒数重新开始
A_Maintenance_ResetSensor();  // 传感器：两项一起重新开始
```

日历周期范围 1～36500 天，小时周期范围 1～65535 h。返回 `MAINTENANCE_OK` 才表示操作成功；实际保存的操作需完成 EEPROM 回读校验。重复设置相同周期不重复写入。
设置与复位接口仅限主循环上下文，要求最近 3 秒内有有效 RTC；不要在 UART 或 SysTick 中断中调用。

### RTC 校准

在页面顶部点击 `YYYYMMDDhhmmss` 输入框，输入十四位日期时间并确认，例如 `20260923143000` 表示 2026-09-23 14:30:00。旁边显示“校准中”“校准成功”或错误提示。输入错误不会修改时钟。

其他项目需要自行提供校时界面时，使用应用层接口：

```c
Maintenance_Date g_target = {2026, 9, 23, 14, 30, 0};
Maintenance_Result result = A_Maintenance_SetRtc(&g_target);
// MAINTENANCE_IN_PROGRESS 表示请求已受理；继续调用 A_Maintenance_Task。
// 随后查询 A_Maintenance_GetRtcSetResult()，MAINTENANCE_OK 才表示回读与保存均成功。
```

校时前要求模块已有有效记录和最近 3 秒内的有效 RTC 回包。流程为“保存待确认记录 → 发送 EE 81 → 查询 RTC 并确认目标 → 保存新的 RTC/累计秒数锚点”。RTC 回读按 2 秒容差确认，整个流程约 10 秒超时。在线校时过程中实际经过的时间由 MCU 毫秒时基补计，亚秒余数在运行期间保留；RTC 本身只有秒级分辨率，轮询和通信延迟会带来秒级量化误差。

校时进行中，周期设置及复位接口返回 `MAINTENANCE_NOT_READY`。请先检查 `SetRtc` 返回值；未受理的 API 请求不会覆盖上一次异步结果。重启后不会保留上次成功提示，未完成的校时则返回时间错误并提示重新校准。

**所有人工校时都必须经过此入口。** 不再使用 RTC 控件直接编辑、其他模块直接下发 EE 81 或绕过模块修改时钟。仅凭两次 RTC 读数无法区分向前调表和真实经过的时间，模块不能自动识别绕过入口的向前跳变。

## 上下文结构体

模块内部在 `A_Maintenance.c` 持有一个 `static Maintenance_Context g_maintenance`，所有 A 接口共用这一实例。接入方只调用接口，不需要创建、清零或传递上下文。模块不导出可写全局变量；F/H 层仍通过结构体指针传递状态，保留内部复用能力。

保存参数、运行状态、硬件状态分别归入 `save`、`state`、`port`。结构体类型采用首字母大写、下划线分词，实例与指针采用 `g_` 加小写名称。以下字段供模块维护和调试查看，业务代码不要绕过接口直接修改。

当前硬件适配器独占一组 SCI9/SysTick 和 EEPROM。移植到其他项目时，将 `Maintenance/` 加入源文件构建并配置头文件搜索路径；按目标硬件调整 H 层的引脚、串口及中断配置，保留 1 毫秒时基，避免重复定义 `SysTick_Handler` 或 `DIS_Callback`。A/F 层接口和维保逻辑无需因接入方改变。首次任务会等待屏幕启动和有效 RTC，复位的时间及存储前置条件保持原样。

| 变量 | 主要字段 | 含义 |
|---|---|---|
| `g_maintenance.save` | `machine / sensor` | 两项目的保存参数 |
| | `*.period_days / *.start_calendar_seconds` | 天数周期及累计时间轴上的秒数起点 |
| | `*.period_hours / *.start_uptime_seconds` | 小时周期及开机秒数起点 |
| | `uptime_seconds` | 最近一次成功保存的累计开机秒数 |
| | `rtc_anchor_seconds / calendar_seconds` | 成对保存的原始 RTC 秒数与累计日历秒数 |
| | `calibration_pending / rtc_target_seconds / sequence` | 校时待确认标志、校时目标秒数与日志序号 |
| `g_maintenance.state` | `rtc / current_day` | 最近 RTC、以 2000-01-01 为 0 的日期序号 |
| | `uptime_seconds / uptime_remainder_ms` | 当前累计开机秒数及不足一秒的部分 |
| | `rtc_seconds / calendar_seconds / calendar_ready` | 当前 RTC 原始秒数、排除校时跳变后的累计秒数及有效标志 |
| | `machine / sensor` | 两项目的过程变量 |
| | `*.elapsed_days / *.remaining_days` | 已过天数不封顶；剩余天数到期为 0 |

| | `*.day_percent / *.hour_percent / *.progress_percent` | 两指标百分比和最终条形进度，均限于 0～100 |
| | `*.countdown_valid / *.hours_valid` | 日历、开机时间的有效标志 |
| | `*.status / status / last_result` | 单项目状态、总状态、最近操作结果 |
| | `reset_all_request / reset_all_result` | 调试器一次性复位请求及结果 |

### 调试时一次性重置两项目

1. 编译并下载新固件，运行到 RTC 正常，确认屏幕日期正确。
2. 暂停并选中 `A_Maintenance_Task` 调用栈帧，在 e² studio 的 Expressions 中将 `g_maintenance.state.reset_all_request` 改为 `1`；该变量现在是 `A_Maintenance.c` 内的静态实例。
3. 恢复运行。主循环等待有效 RTC 和可用存储，用一次提交保存两项目的新起点。
4. 请求自动变为 `0`，`reset_all_result == MAINTENANCE_OK`（0）表示成功。两项目均显示 `0天/周期天`、`0h/周期h`。

该请求每次开机默认关闭，不会在重启后再次复位。不要将默认值改成 1，也不要在循环中重复置位。写入失败会停止本次请求；修复存储后检查当前起点，再决定是否重新请求。
全部记录损坏时，显式 Reset 或该调试请求使用默认周期重建记录；不自动把损坏记录当成全新设备。

## 掉电保存与升级

24C256 的 **0x7800～0x7FFF（2 KiB，32 个 64 字节页）** 专供维保记录使用，其他模块不能占用。原来的 0x7F00、0x7F40 包含在此区域内。

当前记录为 v4：60 字节有效载荷含 CRC32，第 63 字节为提交标记。每次写下一页：先使目标页失效并确认，写入并回读数据，最后提交并再次校验；当前有效记录不覆盖。上电逐页扫描，选择最新完整记录。循环使用 32 页以分散写入次数。

v4 将偏移 12/22 的两项目起点改为累计日历秒数，16 改为原始 RTC 秒数锚点；28～43 的开机时间及小时周期字段保持 v3 布局。44 保存累计日历秒数，48 保存校时目标秒数，52 保存待确认标志（0/1），53～55 保留为零，56～59 保存前 56 字节 CRC32。完整布局也在 `F_Maintenance.c` 的存储函数前注明。升级后不要直接刷回旧固件：旧固件不理解 v4，会忽略新记录。

- 开机时间每累计 60 秒保存一次；设置周期、确认保养完成、首次建立记录、旧版本迁移也会保存。
- 正常通信与连续主循环调度下，突然断电会损失最近尚未提交的不足一分钟左右使用时间。写入正在进行、任务长时间阻塞或存储故障时，不能保证这个上限。
- 每次断电的未保存部分都可能丢失，频繁短时间通断电会累积误差。断电前有可靠通知时可另行增加最终保存流程；本版不假设硬件提供该通知。
- 已有 v1/v2/v3 记录自动升级为 v4，保留原来已经计算出的整天数和周期。旧记录未保存日内起点，因此不能恢复历史不足一天的秒数；升级后从收到有效 RTC 的时刻继续精确累计。
- v1 只有整机记录，新增传感器的日历起点在迁移时设为当前累计秒数；v2/v3 的两个项目分别转换起点。v1/v2 没有开机小时，升级后从零累计；v3 保留已保存的开机秒数及两项目小时起点。
- 最终回读失败时，新记录可能已提交；后续重新加载会恢复实际完整记录，不重复累计已保存的秒数。

普通断电恢复按“已保存累计秒数 + 当前 RTC 秒数 − 已保存 RTC 锚点”补计实际断电时长，因此日历进度不受一分钟保存间隔影响。校时会在修改 RTC 前后各保存一次，避免把不同时间基准直接相减。

如果校时中途断电或确认失败，重启后保留已保存的保养进度，显示时钟异常并要求重新校准；不会自动重发断电前的目标时间。这个情况下无法可靠判断 RTC 在断电前是否已修改，所以不补算这段不确定时长。重新校准后继续累计，已知的保养进度与开机小时仍保留；待重新校准期间开机小时继续按分钟保存。

RTC 异常时日历行显示 `--天/周期天`，小时仍由 MCU 累计并按分钟保存；进度条取仍有效的小时比例，状态提示时间异常。存储异常时显示无效占位并重试读取，不把无法确认的记录显示为正常。

MCU 每秒分帧刷新两项目显示；串口发送忙时顺延，不等待屏幕回包。115200 / 8N1，大彩组态协议，CRC 关闭。中文文本按 GBK 发送。

```text
读取 RTC：  EE 82 FF FC FF FF
RTC 回包：  EE F7 年 月 星期 日 时 分 秒 FF FC FF FF
设置 RTC：  EE 81 秒 分 时 日 星期 月 年 FF FC FF FF
校时输入：  EE B1 11 画面ID 控件ID 11 十四位ASCII时间 00 FF FC FF FF
文本更新：  EE B1 10 画面ID 控件ID 文本 FF FC FF FF
进度更新：  EE B1 10 画面ID 控件ID 四字节大端数值 FF FC FF FF
前景色：    EE B1 19 画面ID 控件ID 两字节RGB565 FF FC FF FF
```

所有 ID 为两字节大端。RTC 字段为 BCD，范围 2000～2099；校验长度、BCD、日期与闰年。

## 硬件与时间边界

- MCU：RA4M1，FSP 3.8，裸机主循环。SCI9 使用 `DIS_UART`、`DIS_Callback`。
- P109/TXD9、P110/RXD9 经 SP3223 连接串口屏；使用匹配的 RS-232 接口。
- P113 `DIS_POWER`、P114 `DIS_EN` 初始化拉高；默认等待 2 秒后开始 RTC 查询。
- 24C256 地址 0x50（A0/A1/A2 接地），P608/SCL、P609/SDA 开漏软件 I²C，P115/WP。
- 模块独占 SysTick 1 ms。仅在 MCU 时基运行时累计开机时间；以后接入 RTOS、深度休眠或停用 SysTick，必须同步改造时基。
- EEPROM I/O 是有超时的同步操作，加载时扫描 32 页，期间中断保持开启。主循环应持续执行，不能把保存放入严格实时的控制中断。
- RTC 必须先校准并由屏幕备用电池维持断电走时。格式正确不代表实际日期正确。
- 正常 RTC 读数早于上次已接收或保存的秒数锚点时，会暂停日历结果；通过模块受控校时则允许前调、后调且保持保养进度。
- 累计日历秒数和开机秒数采用 uint32_t，在 UINT32_MAX 处饱和以避免回绕。日历累计轴初始值采用自 2000 年起的秒数，后续人工校时不改变该累计轴；它不是可直接格式化显示的公历时间。毫秒调度计数正常回绕不影响累计。

## 编译与验证

MCU 工程：在 e² studio 中打开 `Maintenance_Manager` 并编译。命令行也可运行：

```text
python tools/check_maintenance.py
```

脚本先运行主机测试，再用本机 ARM GCC 编译、链接，输出到 `tmp/maintenance-build`；可传 `--host-only`、`--arm-gcc`、`--host-gcc`。回归测试随源码保存在 `tools/tests/`；根目录被忽略的 `tests/` 是原本的本地副本，不参与构建。测试通过包含 A/F 层实现检查私有实例和日期/RTC 辅助函数，不为测试增加生产导出接口。
